# 직전 연결 코드 복원 — Android 0.6.9 / Watch 0.5.12

**한국어** · [English](ROLLBACK_0.5.12_EN.md)

브랜치: `fix/watch-background-reconnect`. `c3f3f53` 당시의 Android **0.6.9-local** / Watch **0.5.12** 원본으로 복원했습니다. 워치는 당시 **원본 빌드 36 설치 파일**을 직접 사용했습니다. Android는 원본 실행 코드·리소스를 유지하고 덮어 설치용 번호만 **28**로 올렸습니다. [원본 코드 APK](../artifacts/android/FoldBridge-Local-0.6.9-original-code-28.apk).

## 복원 이유와 현재 파악한 범위

0.5.13 설치 후 워치 앱을 열어야 연결된다는 사용자 보고가 있었습니다. 앱 자체 기록에서는 폰의 연결 서비스가 켜져 있고 워치 연결·수신 등록도 반복되지만, 워치는 시작 신호 대기 중 연결이 종료돼 인증을 끝내지 못했습니다. 단순 검색 실패나 폰 서비스가 꺼진 상태와 구분합니다.

해당 워치 기록의 앱 연결 취소 횟수와 오류 집계는 0이었습니다. Android 0.6.10에서 새로 추가한 수신 등록 해제 처리도 해당 폰 프로세스에서는 실행 횟수 0이어서 그 경로를 직접 원인으로 확정하지 않습니다. 0.5.13의 재접속 재개·검색 정리·위치 세션 복원 변경 중 이 현상의 직접 원인이 있는지는 아직 확정하지 못했습니다. 이전 코드로 복원하는 것은 원인 분리를 위한 대응이며 장시간 연결의 완전 해결을 뜻하지 않습니다.

## 앞선 빌드 39 복원 후 원인 분석 — 2026-11-08

복원 후에도 잠긴 워치에서 폰의 연결·새로고침만으로 연결되지 않는다고 사용자가 보고했습니다. 코드만 되돌린 상태와, 이전에 연결 유지 세션이 살아 있던 실행 상태는 구분해야 합니다.

확인한 앱 코드의 복원 경로 결함은 다음과 같습니다.

- `LocationKeepAlive.start()`는 앱이 전면 `.active`가 아니면 반환합니다. 저장된 연결 유지 설정이 켜져 있어도 백그라운드 재실행만으로 위치 연결 유지 세션을 재개하지 못합니다. 롤백 후 Mac의 화면 비활성 실행 명령으로 한 번 시작한 것만으로는 이 준비가 충분하지 않았습니다.
- `willRestoreState`에서 상대가 `.connecting`이면 재검색을 20초 뒤 앱 타이머에 예약합니다. `reconnect()`는 같은 `.connecting` 대상을 만나면 반환합니다. 이 복원 경로에는 즉시 복구 검색을 시스템에 등록하는 동작이 빠져 있고, 지연 앱 타이머는 중단된 앱을 깨우지 못합니다.
- 앱을 열면 `setActive(true)`에서 복구 검색과 대기 중 인증 재개를 실행하고, SwiftUI 전면 전환 처리에서 연결 유지도 재개합니다. 따라서 앱 열기가 여러 복구 동작을 한꺼번에 실행하는 경로가 됩니다.

실제로 읽은 마지막 워치 저장 기록은 빌드 39에서 `active=false`, `continuousRequested=false`, `recoveryScanning=false`, 상대 `.connecting`이었고 이후 새 실행 기록이 없었습니다. 이는 현재 실행 중인 상태를 실시간으로 측정한 값과 구분합니다. 이후 기록에는 전면 전환 직후 구독·인증이 완료됐습니다. 사용자가 직접 앱 열기 또는 연결 중지 조작을 했다고 답했으므로, 이 구간을 무조작 자동 복구 성공으로 해석하지 않습니다.

폰의 저장 상태가 실행 중이라고 남아 있어도 실제 서비스는 종료돼 있을 수 있는 진단상의 결함도 찾았습니다. `BridgeService.onDestroy()`는 상태를 중지로 바꾸지만 저장 상태 파일을 다시 쓰지 않습니다. 이번에는 실제 서비스 목록과 비교해 저장된 값을 그대로 현재 상태로 간주하지 않았습니다. 폰 서비스 종료가 사용자 조작 없이 발생했다고 단정하지 않습니다.

이 내용은 **현재 복원본에서 앱 열기에 의존하는 구체적인 코드 경로**를 설명합니다. 0.5.13의 최초 반복 연결 종료를 어느 개별 변경이 유발했는지는 별도 미확정이며, 이 분석만으로 장시간 잠금·반복 거리 복귀가 해결됐다고 표시하지 않습니다.

## 유지하는 데이터와 설치 방식

기존 앱과 같은 앱 ID·서명 키로 덮어 설치합니다. 등록 정보·암호화 키·차량 버튼 설정을 삭제하지 않습니다. 앱 삭제나 새 페어링은 하지 않습니다.

Android는 설치된 코드 27 위에 원본 코드 25 APK를 덮어 설치하는 작업을 거부했습니다. 데이터 삭제 없이 적용하기 위해 원본 코드로 다시 만든 APK의 Manifest 설치 번호만 28로 높였습니다. Gradle과 직접 빌드 도구도 이 번호를 사용합니다. Java 실행 코드·리소스·연결 동작에는 변경을 추가하지 않았습니다. 앱 자체 진단의 `build` 값은 원본 코드 그대로 25이며, Android 패키지의 설치 번호 28과 다릅니다.

원본 APK와 새 APK의 `classes.dex`는 바이트 단위로 같고 SHA-256은 `0b6a5afd8556c96394b7a54bc5dc649cd18487e8a3e4ec907b6af42e1fce88b1`입니다. 서명 파일을 제외한 APK 항목 중 다른 파일은 `AndroidManifest.xml` 하나뿐입니다. 워치는 재빌드한 39 대신 보관된 원본 빌드 36을 직접 설치했으며, 저장소의 앱 코드와 워치 버전 정보도 원본으로 되돌렸습니다. 이전 실행 중이던 프로세스·OS의 Bluetooth 상태까지 설치로 되돌릴 수 있다는 뜻은 아닙니다.

## 적용 상태 — 2026-11-08

- 워치 0.5.12 / **원본 빌드 36**: 기존 앱 위에 원본 설치 파일로 설치 완료.
- Android 0.6.9-local / **설치 코드 28**: 원본 실행 코드·리소스로 덮어 설치 완료. 자체 진단의 빌드 25 표기는 원본 유지 결과입니다.
- 저장된 워치 등록과 연결 유지 설정이 남아 있었습니다. 설치 준비를 위해 워치를 잠금 해제한 뒤 원본 앱을 전면 실행했고, 양쪽 화면에서 연결·인증 완료 상태가 표시됐습니다. 그 뒤 워치를 시계 화면으로 돌렸습니다.
- 초기 준비 중 백그라운드에서는 구독 후 시작 신호 대기 중 연결이 반복 종료됐습니다. 전면 실행 후 연결됐으므로 원본 앱 복원과 앱 진입 없는 재연결의 완전 해결을 같은 결과로 취급하지 않습니다. 추가적인 장시간·거리·재부팅 시험은 진행하지 않았습니다.
- 마무리는 기존 요청에 따라 폰의 **설정 → 연결 중지**를 눌렀습니다. 화면이 **워치 연결**로 돌아왔으며 등록·키·차량 설정은 지우지 않았습니다. 다음 사용은 폰의 **워치 연결**로 서비스를 켭니다.
- Mac의 워치 화면 공유·갤럭시 미러링을 종료했습니다. 시스템 로그는 수집하거나 이 변경에 포함하지 않았고 실제 차량 명령도 실행하지 않았습니다.

## 원본과의 추가 비교 — 2026-11-08

폰에서 실제 설치된 APK를 가져와 비교했습니다. 원본 APK와 실행 코드(`classes.dex`)·리소스는 같고, Manifest 설치 번호와 그 변경에 따른 서명 파일만 다릅니다. 서명 인증서도 같습니다. 설치된 APK 전체는 이번 원본 코드 복원용 APK와 바이트 단위로 일치합니다. 저장소의 Android·watch 앱 소스는 원본 `c3f3f53`과 같으며 Android 설치 번호를 지정하는 두 빌드 파일만 다릅니다.

Mac 작업 폴더의 Xcode 실행 스킴에는 커밋되지 않은 차이가 별도로 남아 있습니다. Xcode 스킴 형식과 실행·테스트·프로파일 항목이 추가된 상태이며, 이번 워치 설치는 그 스킴으로 재빌드하지 않고 보관된 원본 설치 파일을 사용했습니다. 이 사용자 작업 파일은 변경하거나 커밋하지 않습니다. 설치된 워치 내부 실행 파일을 다시 추출해 해시 비교한 결과는 아닙니다.

이전에 폰 버튼만으로 성공했던 기록과 이번 실패 기록의 실제 차이는 다음과 같습니다.

| 항목 | 이전 성공 기록 | 원본 복원 후 실패 기록 |
| --- | --- | --- |
| 워치 UI 전면 여부 | 백그라운드 | 백그라운드 |
| 연결 유지 요청 | 켜짐 | 켜짐 |
| 복구 검색 상태 | 켜짐 | 꺼짐 |
| 폰의 시작 신호 수신 | `remote.wake` 기록 있음 | 비교한 반복 실패 구간에는 없음 |
| 인증 | `handshake.commit` → `authenticated` | `awaitingBootstrap` 중 연결 종료 반복 |

현재 폰 기록에는 구독 선택과 시작 신호 전송 경로가 반복 실행되고, 워치는 구독까지 성공한 후 시작 신호를 받기 전에 종료되는 양상이 남아 있습니다. 단순히 위치 연결 유지 토글이 꺼졌거나 다른 앱 코드가 설치됐기 때문이라고 설명할 수 없습니다. `bootstrapSent`는 폰 코드가 전송 경로에 들어갔다는 집계이며 워치 전달 완료의 증명은 아닙니다. 복구 검색 상태 차이도 관측 결과이며 직접 원인으로 확정하지 않습니다. 시작 신호가 워치에 전달·처리되지 않는 이유와 연결 종료를 유발한 주체는 아직 미확정입니다. 저장 설정 전체의 과거 스냅샷이 없어 당시 모든 설정과 현재 설정이 동일하다고도 단정하지 않습니다.

이번 추가 비교에서는 워치 앱을 열거나 새로고침·등록 해제·설정 변경을 하지 않았고, 시스템 로그도 사용하지 않았습니다.

## 폰 재부팅과의 시간 관계 — 2026-11-08

시스템 로그 대신 폰 시계와 `/proc/uptime`을 읽어 계산한 최근 부팅 시각은 **2026-11-08 오전 3:14경 KST**입니다. 앞선 폰 버튼 단독 백그라운드 인증 성공 기록은 같은 날 **오전 1:50**, 원본 복원 뒤 반복 실패 기록은 **오전 4:44 이후**입니다. 성공과 실패 사이에 폰 재부팅이 있었음은 확인되지만, 재부팅이 직접 원인이라는 인과관계까지 입증한 것은 아닙니다. 이미 재부팅 이전부터 시작된 실패가 있었는지도 이 자료만으로 확정하지 않습니다.

현재 실제 폰 연결 서비스는 실행 중이며 광고·구독 선택·시작 신호 전송 경로가 동작합니다. 따라서 현재 실패를 부팅 후 폰 서비스가 시작되지 않았기 때문이라고 설명하지 않습니다. 재부팅·Bluetooth 스택 재시작 후 기존 연결 보존 상태와 새 인증 시작 상태가 어긋나는 경로가 조사 대상입니다. 원본의 부팅 수신 처리는 저장된 사용 설정·잠금 해제·권한을 확인한 뒤 서비스를 재개하지만 워치 쪽 인증 완료를 보장하는 동작은 아닙니다. 추가 재부팅이나 설정 초기화는 수행하지 않았습니다.

## 계속 남는 항목

1. 워치 앱을 열지 않아도 연결·인증이 끝나고, 잠금 중 다시 끊긴 뒤에도 복구되는 문제.
2. 수시간 잠금·대기 중 연결과 새 알림 수신 유지.
3. 반복적인 실제 거리 이탈·복귀 후 양쪽 앱 실행·새로고침 없는 재연결.
4. 실제 재부팅과 최초 잠금 해제 후, 기존 등록으로 앱 실행 없이 연결 복구.

폰의 **워치 연결**은 중지된 연결 서비스를 켜는 버튼이고, **연결 새로고침**은 켜진 서비스에서 복구를 요청하는 버튼입니다. 버튼이 새로고침으로 바뀌는 것만으로 워치 인증 성공을 뜻하지 않습니다.
