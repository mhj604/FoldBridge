# Android 0.6.10 / Watch 0.5.13: 버튼 없는 복구 경로

**한국어** · [English](WATCH_0.5.13_AUTOMATIC_RECOVERY_EN.md)

수정 후보 브랜치: `fix/watch-background-reconnect`. Android **0.6.10-local / 코드 26**, Watch **0.5.13 / 빌드 38**. [APK](../artifacts/android/FoldBridge-Local-0.6.10.apk). 기존 등록·암호화 키·차량 버튼 설정을 유지합니다.

## 이번 변경

1. `didFailToConnect` 이후에도 백그라운드에서 다음 연결과 서비스 검색을 즉시 시스템에 등록합니다. 기존 실패 경로에는 앱 타이머만 예약되는 경우가 있었습니다.
2. 전면에서 설정된 재시도 대기가 앱이 백그라운드로 전환된 뒤 복구를 막지 않게 합니다. 새 백그라운드 실행 기회를 받았을 때도 오래된 앱 타이머 대기를 정리합니다.
3. 복원된 연결이 `.connecting` 상태여도 검색을 즉시 등록합니다. 20초 뒤 앱 타이머에만 의존하지 않습니다. 서비스 대기 중에 실행 기회를 받으면 서비스 재탐색도 이어갑니다.
4. 취소가 완료됐지만 중단된 타이머 때문에 남아 있던 전환 상태를 정리합니다. 연결 콜백의 같은 식별자 객체도 현재 대상으로 일치시킵니다.
5. 인증 완료 후 복구 검색과 남은 재시도 작업을 정리합니다. 정상 연결을 주기적으로 끊거나 빈 heartbeat를 보내지 않습니다.
6. 폰에서 워치가 CCC 수신 등록을 해제하면 앱 세션 점유를 놓고 광고를 재개합니다. 물리 LE 링크가 다른 서비스 때문에 살아 있더라도 새 연결 검색을 막지 않습니다. 기존 물리 링크를 취소하지 않습니다.
7. 빌드 38에서는 이미 켜 둔 위치 연결 유지의 `CLBackgroundActivitySession`을 시작 시 보관하고 백그라운드 재실행 직후 재생성합니다. 이전에는 앱 전면에서만 위치 유지가 재개돼 프로세스 복원 후 꺼진 상태가 남았습니다. 기존 허용 권한과 사용자 켜짐 설정으로만 복원하며 새로운 Always 위치 권한을 요청하지 않습니다. Core Location이 세션을 사용할 수 없다고 보고하면 연속 처리 가능 상태도 해제합니다. [Apple 세션 API](https://developer.apple.com/documentation/corelocation/clbackgroundactivitysession).

0.6.9 / 0.5.12에서 변경한 구독 직후 시작 신호와 저장 키 인증 순서는 유지합니다. 밀린 알림을 재생하지 않고 새 인증 이후의 새 알림만 전달하는 정책도 유지합니다.

## 실제 기기에서 기록된 동작 — 2026-11-08 KST

Bluetooth 중단·거리 복귀와 첫 프로세스 복원 기록은 빌드 37에서 얻었습니다. 위치 유지 복원을 추가한 최종 빌드 38도 덮어 설치했습니다.

| 상황 | 기록된 결과 | 범위 |
| --- | --- | --- |
| 폰 Bluetooth 끄기/켜기 | 실제 연결 종료 후 워치의 연결·구독·인증 자동 완료. 양쪽 새로고침 0 | 폰은 설정 화면, 워치 앱은 백그라운드 |
| 워치 앱 프로세스 종료 | 에이전트가 앱을 다시 실행하지 않은 상태에서 새 프로세스 `launch → restore.2 → authenticated` 기록 | 앱 프로세스 종료 복원이며 기기 재부팅과 구분 |
| 실제 거리 이탈·복귀 | 사용자가 워치를 가지고 멀어졌다 복귀. 워치에 연결 시간 초과 종료(`CBError` 6) 후 자동 연결·인증 기록. 양쪽 새로고침 0 | 복귀 뒤 워치 앱 전면 전환 없음 |
| 잠근 워치의 프로세스 종료·복원 (빌드 38) | 새 프로세스의 위치 세션 재개 → 저장 연결 복원 → 인증이 모두 `active=false`로 기록. 워치 새로고침 0, 전면 전환 없음 | 사용자가 잠근 상태로 둔 뒤 원격 화면 공유도 종료한 조건 |
| 잠금 상태에서 폰 새로고침 | 사용자 보고: 0.5.12에서도 워치를 잠금 해제하지 않고 연결됨 | 사용자 관찰이며 잠금 시간은 측정하지 않음 |

거리 이탈 때 종료 기록부터 인증까지 약 16초였습니다. 이 시간은 밖에 있던 시간도 포함하며, 실제 복귀 시각을 측정한 재연결 지연은 아닙니다. 새 프로세스의 이벤트도 모두 `active=false`였습니다. 로컬 진단 파일의 기기 식별자·개인 알림·원본 로그는 공개 저장소에 올리지 않습니다.

## 잠금 관찰에서 다시 발생한 미해결 현상

빌드 38의 잠금 중 프로세스 복원·인증 성공 뒤 약 95초 후 연결 종료가 기록됐습니다. 이어 두 차례 자동 연결·구독까지 진행했지만 시작 신호 대기(`awaitingBootstrap`) 중 다시 종료됐고, 폰은 광고 중인 대기 상태로 남았습니다. 워치의 해당 종료 콜백은 오류 없음으로 기록됐으며 앱의 연결 취소 횟수는 0, 백그라운드 한도 경고도 없었습니다. 따라서 시스템 한도나 위치 권한을 원인으로 확정하지 않습니다. 이 기록 때문에 **잠금 상태의 지속 연결·알림 전달은 아직 해결 완료가 아닙니다.** 폰의 전송 대기 수가 0이 됐다는 사실만으로 복원 뒤 알림 수신 성공을 판정하지 않습니다.

## 장시간 잠금·재부팅 범위

자동 복구 코드는 장시간 잠금에도 같은 시스템 연결 요청·서비스 검색·백그라운드 실행 기회를 사용합니다. 잠금 시간만을 이유로 정상 연결을 취소하는 코드는 없습니다. 다만 수시간 또는 밤새 잠금 동작을 이번 짧은 관찰로 완료 처리하지 않습니다.

Android는 기존 `BOOT_COMPLETED` / 패키지 업데이트 / Bluetooth 켜짐 수신과 알림 수집 서비스 재연결에서 활성화된 연결 서비스를 복구합니다. 워치는 시스템의 Core Bluetooth 상태 복원과 허용된 백그라운드 갱신에서 저장된 상대를 재개합니다. 이번 작업에서 두 기기 자체를 재부팅하지는 않았습니다.

재부팅 후 최초 잠금 해제 전에는 앱이 사용하는 보호된 저장소와 키에 접근할 수 없습니다. 워치 키는 `AfterFirstUnlockThisDeviceOnly`, Android 설정은 자격 증명으로 보호된 저장소에 있습니다. **일반 잠금 상태**와 **재부팅 후 최초 잠금 해제 전**은 다릅니다. 최초 해제 이후 다시 잠그는 것은 매 연결마다 해제해야 한다는 뜻이 아닙니다. [Apple 키 접근 조건](https://developer.apple.com/documentation/security/ksecattraccessibleafterfirstunlockthisdeviceonly) · [Android Direct Boot](https://developer.android.com/privacy-and-security/direct-boot).

watchOS는 Bluetooth 백그라운드 실행과 반복 재연결에 시스템 한도를 둡니다. 앱 코드는 허용된 실행 기회에서 복구하며, 실행을 항상 즉시 강제하거나 한도를 없애지 않습니다. [Apple 공식 설명](https://developer.apple.com/videos/play/wwdc2022/10135/).

따라서 현재 남은 항목은 **잠금 복원 뒤 다시 끊기는 현상의 원인·수정**, **수시간 잠금 후의 유지·복구**, **실제 재부팅 후 최초 해제 뒤 자동 복구**입니다. 실제 거리 복귀와 잠금 중 프로세스 종료 복원은 위에 기록한 조건에서 성공했습니다. 사용자에 의한 앱 강제 중지는 OS의 프로세스 회수와도 구분합니다.

## 다음 사용과 작업 종료

- 일상 사용에서는 폰의 연결 서비스를 켜 두고 가까이 돌아오면 자동 복구를 기다립니다. 등록을 다시 만들지 않습니다.
- 폰 **연결 중지**는 사용자가 명시적으로 서비스를 끈 상태입니다. 이때에는 폰의 **워치 연결**을 한 번 눌러 다시 켭니다.
- 작업 종료 때에는 등록을 유지하고 실제 연결과 Mac 진단 연결만 중지합니다.
