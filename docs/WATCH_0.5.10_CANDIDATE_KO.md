# Watch 0.5.10 / Android 0.6.8: 백그라운드 재연결 수정 후보

**한국어** · [English](WATCH_0.5.10_CANDIDATE_EN.md)

이 변경은 `fix/watch-background-reconnect` 브랜치의 수정 후보입니다. Android **0.6.8-local / 코드 24**, Watch **0.5.10 / 빌드 34**를 같은 앱 위에 설치합니다. 기존 등록·키·차량 버튼 설정을 지우지 않습니다. 기본 배포의 모든 조건을 통과한 안정 버전이라는 뜻은 아닙니다.

## 확인한 원인과 변경

1. 워치가 백그라운드에서도 실행되고 있었지만, 폰의 FoldBridge GATT 서비스가 일시적으로 없을 때 연결을 취소하고 즉시 재접속했습니다. 전체 서비스 목록을 다시 읽고, 서비스가 여전히 없으면 물리 링크를 유지하며 2~30초 간격으로 서비스 복구를 기다리도록 바꿉니다. 서비스 변경·새 광고·연결 유지 콜백에서도 복구를 진행합니다.
2. 폰 프로세스가 다시 시작됐는데 워치는 기존 암호화 세션이 유지됐다고 판단하는 상태도 읽었습니다. 구독 후 750ms 동안 새 인증이 시작되지 않으면, 저장된 상대가 있는 경우에만 인증 재시작 요청을 한 번 보냅니다. 정상 유휴 연결에 주기적인 깨우기 요청을 보내지는 않습니다.
3. watchOS가 구독을 복원한 채 새 인증을 시작하면 Android는 CCC 재작성 없이도 제한된 새 `commit` 프레임을 받아 통신을 복원할 수 있습니다. 이후 저장된 공개 키와 암호화 확인을 모두 통과해야 인증됩니다. 일반 데이터나 임의의 물리 연결로 상대를 선택하지 않습니다.
4. 연속 연결 실패에는 2~30초의 재시도 간격을 적용합니다. 즉시 실패→취소→재시도가 반복되는 경로와 이미 끊긴 연결에 대한 불필요한 취소를 제거합니다. 최초 연결 종료 시의 즉시 재연결 요청과 OS가 관리 중인 자동 재연결은 유지합니다. 반복 실패의 지연 재시도에는 OS가 허용하는 앱 실행 기회가 필요합니다.
5. 서비스 대기 횟수와 실제 연결 실패 내용을 진단에 추가합니다. 메시지 본문이나 개인 키는 기록하지 않습니다.

## 실제 기기 기록과 한계

2026-11-07 같은 서명으로 두 기기에 덮어 설치했습니다. 설치 후 새 워치 코드를 준비하려고 앱을 한 번 실행했고, 이후 시계 화면으로 보냈습니다. 따라서 설치 자체를 완전 무조작 실행의 증거로 보지 않습니다.

초기 수정본은 백그라운드 인증에 성공했지만, 폰 프로세스 재시작 후 연결 종료가 반복되는 사례도 확인했습니다. 워치가 연결을 취소한 경우와 운영체제 연결 종료는 구분했습니다. 따라서 잠금 해제만으로 항상 연결되는 문제가 완전히 해결됐다고 주장하지 않습니다. 실제 거리 이탈·복귀와 장시간 중단 후 복구도 별도 확인이 필요합니다.

최종 수정본에서는 워치가 시계 화면에 있는 동안 폰 프로세스를 종료하고 폰 앱만 다시 열었습니다. 같은 워치 프로세스가 `active=false` 상태에서 32초 간격으로 서비스 탐색·구독·인증 시작을 재시도했지만, 인증 중 연결 종료 콜백이 이어졌습니다. 앱의 연결 취소·프로토콜 실패 기록은 없었습니다. 따라서 폰 재시작 후 백그라운드 재인증은 이 사례에서 성공하지 않았습니다. 이 기록만으로 운영체제 연결 종료의 최종 원인을 단정하지 않습니다. 복원 구독의 새 Android 경로는 실행 횟수 0이므로 실제 통과했다고 표기하지 않습니다. 실제 차량 명령은 실행하지 않습니다. 기기 원본 기록·식별자·서명 키는 공개하지 않습니다.

## 버튼 이름과 작업 종료

폰의 **연결 새로고침**은 연결 서비스가 이미 켜져 있을 때 표시됩니다. **워치 연결**은 서비스를 중지한 상태에서 표시됩니다. 두 이름을 같은 상태의 버튼으로 안내하지 않습니다.

작업 종료 시에는 **설정 → 연결 중지**로 실제 연결만 중지합니다. 등록한 워치·휴대폰 등록 해제는 사용하지 않습니다. 중지를 선택하면 자동 연결도 꺼지므로 다음 사용 때 폰의 **워치 연결**을 한 번 눌러 서비스를 켭니다. 일반 거리 이탈과 명시적인 연결 중지는 다릅니다.
