## 수행 방법

사용자가 폰은 그대로 두고 워치를 실제 Bluetooth 범위 밖으로 가져갔다 돌아오는 동작을 3회 수행했습니다. 워치 앱·양쪽 연결/새로고침은 누르지 않도록 안내했고, 2·3회차는 암호 잠금을 유지하도록 안내했습니다. 사용자가 매회 복귀를 알려 주었고 REA CLI로 앱 자체 기록을 수집했습니다. 물리 이동을 자동화한 것은 아닙니다.

| 회차 | 폰 native 종료 누적 | 복귀 후 인증·읽기 수신 |
| --- | --- | --- |
| 1 | 3 → 4 | 자동 복원 |
| 2 | 4 → 5 | 자동 복원 |
| 3 | 5 → 6 | 자동 복원 |

세 번 모두 실제 종료 카운터 증가와 새로운 인증을 확인했습니다. 마지막 폰 상태는 `authenticatedLink=true`, `deliveryResponsive=true`, `refreshCount=0`, `softRefreshCount=0`, `pending=0`이며 읽기 횟수도 복원 후 증가했습니다.

마지막 워치 잠금 조회도 `passcodeRequired=true`였습니다. 마지막 워치 상태는 네이티브·SwiftUI 모두 `background`, `active=false`, 인증·연결 정상, `lastError` 빈 값, `failureCounts={}`, 앱의 연결 취소 0회를 기록했습니다. 이 회차들에서 광고 기반 재설정·취소 완료 분기는 실행되지 않았으므로 해당 분기의 전체 실행 범위를 확인했다고 표현하지 않습니다.

## 수집 범위

- 1·3회차는 약 5초 간격 표본에서 단절 → 인증·수신 복원을 관찰했습니다.
- 2회차 실제 단절 전에 최초 15분 수집기가 종료됐습니다. 복귀 직후 새로 읽은 앱 자체 누적 종료 횟수, 마지막 종료 시각·재인증 시각과 현재 수신 상태로 복원을 확인했습니다. 이 구간 전체를 연속 표본으로 읽었다고 표현하지 않습니다.
- 실제 Bluetooth 범위에 다시 들어온 순간은 측정하지 않았습니다. 단절부터 재인증까지의 시간에는 멀리 머문 시간이 포함되므로 **복귀 후 연결 지연으로 사용하지 않습니다.**
- 기존 [30·60·90초 무선 중단 시험과 10분 잠금 관찰](LOCKED_RECOVERY_TEST_2026-11-18_KO.md)과 이번 실제 이동 결과는 별도 조건입니다.

**실제 거리 복귀 3회는 모두 성공했습니다.** 이번 작업에서 추가 연결 수정이 필요한 실패는 재현되지 않았습니다. 수시간 잠금 추가 시험은 사용자 요청에 따라 이번 범위에서 제외했습니다. 모든 환경·이후 모든 복귀나 OS 프로세스 종료 뒤 복원까지 보장하는 결과는 아닙니다. 메인 화면 자동 표시 조사는 계속 보류합니다.
