## 앞선 추정 정정

사용자는 거리 이탈 후 복귀 때 **앱이 보이지 않아도 자동으로 연결됐다**고 보고했습니다. 화면이 저절로 보였던 경우도 차량 제어 창이 아닌 연결 상태·새로고침이 있는 메인 화면이라고 명확히 했습니다. 따라서 0.5.21 위치 복원이 화면 표시의 직접 원인이라고 확정하거나 위치 코드 롤백을 우선 적용할 근거는 부족합니다. 위치 활동이 표시 정책에 영향을 줄 수 있다는 일반 문서와 특정 기기 현상의 인과관계를 구분합니다.

## 발견된 기록 오류와 보완

기존 `setActive(false)`는 SwiftUI가 `inactive` 또는 `background`인 경우 모두 `lifecycle.background`로 기록했습니다. 손목 내림·화면 일시 비활성화·앱 이탈을 그 이벤트 이름만으로 구분할 수 없었습니다. 일반 이벤트는 128개로 제한돼 서비스 탐색 재시도가 화면 관련 기록을 밀어낼 수도 있었습니다.

빌드 60에서는 다음을 기록합니다.

- 실제 SwiftUI `scene.active`, `scene.inactive`, `scene.background`를 별도로 남깁니다. 이전의 모호한 이벤트 이름은 `lifecycle.nonactive`로 바꿉니다.
- 매 이벤트에 네이티브 `applicationStateName`과 알려진 `scenePhase`를 함께 기록합니다. `active`와 실제 네이티브 상태를 혼동하지 않습니다.
- 별도 앱 자체 파일 `watchbridge-display-events.json`에 최근 256개의 화면·앱 시작·인증·위치 자격 변경 이벤트를 보관합니다. GATT 재시도는 이 화면 기록을 밀어내지 않습니다.
- 알림 기본 동작, 앱 내부 차량 제어 진입, 차량 위젯 진입, 기존 빠른 제어 Intent를 고정된 이름으로 구분합니다. 알림 내용·발신 앱·차량 버튼·좌표는 이 기록에 남기지 않습니다.

표시 기록은 **원인을 확인할 수 있게 하는 보완**이며 자동 화면 표시를 막은 수정이라고 주장하지 않습니다. 공개 API가 알림/위젯 외의 모든 외부 활성화 이유나 손목·Crown 동작을 알려 주지는 않습니다. 원인을 알 수 없는 전환은 unknown으로 남겨야 합니다. `view.main.appear`도 단독으로 실제 화면 표시를 증명하지 않으며 네이티브 상태와 함께 해석합니다.

## 유지한 동작과 남은 문제

현재 작동한 위치 유지·읽기 수신·거리 복구를 되돌리지 않습니다. 시스템 설정의 자동 선택은 앞서 꺼 둔 상태를 유지합니다. 새 차량 명령·진단 알림·강제 거리/잠금 실험·시스템 로그·관리자 인증은 사용하지 않았습니다. 일반 QA나 별도 테스트 실행도 하지 않았습니다.

메인 화면이 다시 나타나는 정확한 진입 원인은 아직 미확정입니다. 새 기록에 알림/위젯 진입 표식이 있으면 그 경로를 조사하고, 표식 없이 네이티브 background→active이면 외부 재활성화로 분리합니다. inactive→active만으로는 백그라운드에서 앱이 새로 열렸다고 판단하지 않습니다. 앞선 위치 롤백 제안은 확인 전 자동 적용하지 않습니다.
