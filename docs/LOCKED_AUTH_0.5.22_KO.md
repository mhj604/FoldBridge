2026-11-15. Android **0.6.16-local / 코드 38**, Watch·차량 위젯 **0.5.22 / 빌드 53**의 수정 후보입니다. 기존 앱에 덮어 설치하며 등록·상대 키·개인 키·차량 설정은 유지합니다. [Android APK](https://github.com/mhj604/WatchBridge/releases/download/connection-v0.5.22/FoldBridge-Local-0.6.16.apk).

## 수정한 경로

0.5.21의 잠금 기록에서는 구독 직후 인증 도중 오류 없는 연결 종료가 반복됐습니다. 앱의 명시적 연결 취소는 없었고, 폰의 공유 GATT 서버는 상대 연결·구독을 유지하는 반면 워치 앱은 종료 콜백을 받았습니다. 이 두 앱의 연결 수명이 일치하지 않았습니다.

이번 수정은 다음 순서로 저장된 상대를 다시 인증합니다.

1. 재연결 때 캐시된 특성으로 탐색 완료 콜백을 직접 만들지 않고 서비스·특성을 다시 탐색합니다.
2. 새 폰의 TX 특성은 `READ | INDICATE`를 제공합니다. 저장된 상대의 짧은 인증 요청을 먼저 쓰고, 네이티브 쓰기 완료 콜백에서 응답을 읽습니다. 인증 응답을 받기 위해 먼저 알림 구독을 켜지 않습니다.
3. 폰은 기존 상대 키로 요청을 확인합니다. 공유 GATT에 이전 구독이 남아 있어도 짧은 재인증은 읽기부터 시작합니다. 폰의 암호화 확인 수신과 워치의 `ready` 수신을 마친 후 새 알림 구독을 받습니다.
4. 읽기와 indication으로 같은 응답이 도착하면 한 번만 처리합니다. 대기 중인 인증 읽기·`ready`·구독 설정이 남아 있는 동안 앱이 백그라운드 작업을 먼저 완료하지 않습니다.

오류 없는 단순 연결 종료만으로 빠른 인증 지원을 끄던 저장 동작도 제거했습니다. 이전 잘못된 비활성 표시는 Local 프로필에서 한 번 초기화합니다. 상대 등록·키는 초기화하지 않습니다. 복원된 같은 특성은 기기·서비스·특성 식별자로 식별하며 명시적으로 무효화된 서비스 객체는 제외합니다. 실제 비교 기록에서 객체 불일치가 종료 원인으로 입증된 것은 아닙니다.

폰의 MTU 추정치는 indication 조각의 보수적인 하한일 수 있습니다. 읽기 응답을 이 값으로 짧게 자르면 클라이언트가 값의 끝으로 판단하므로, 읽기에서는 현재 offset 뒤의 나머지 값을 넘겨 실제 ATT 스택이 처리하도록 수정했습니다. 이 읽기 오류는 개발 중 후보에서 발견·수정한 문제이며 0.5.21의 기존 종료 원인으로 소급하지 않습니다.

## 전송 형식과 호환

기존 P-256 상대 키, 양쪽 새 32바이트 nonce, HKDF/HMAC 문맥과 AES-GCM 확인은 유지합니다. 짧은 resume 응답의 직렬화만 `FBR 02 + 종류 1바이트 + nonce 32바이트 + proof 32바이트`의 69바이트로 줄입니다. 기존 8바이트 프레임 헤더를 포함하면 77바이트이며 ATT 값 크기가 충분할 때 한 프레임입니다. 이전 폰의 indication 전용 특성에서는 기존 JSON 인증을 사용합니다. 새 읽기 경로를 사용하려면 양쪽 버전을 함께 업데이트하세요.

읽기용 응답은 현재 상대의 인증 응답·암호화된 준비 완료 응답만 보관합니다. 알림 기록·차량 명령을 재생하는 저장소가 아닙니다. 연결 전 알림 배제, 실제 인증 상태에 따른 폰 알림, 차량 명령 중복 억제, 알림 레이아웃은 유지합니다.

## 최초 준비와 남은 제한

덮어 설치 후 위치 세션은 `restore-requested`일 수 있습니다. 이는 `eligible`이나 실제 실행 보장이 아닙니다. 이번 작업에서 사용자가 최종 빌드를 한 번 열고 시계 화면으로 돌아온 뒤 다시 암호 잠금했습니다. 이후 폰 서비스만 중지·시작하며 워치 앱은 다시 열지 않는 경로를 사용합니다. 이 설치 후 준비와 매번 재연결할 때 워치 앱을 여는 요구를 구분합니다.

Apple은 watchOS Bluetooth 백그라운드 실행·재연결 예산을 제한합니다. 위치 실행 기회와 Bluetooth 모니터의 실행 보장은 동일하지 않습니다. [Apple의 동작·제한 설명](https://developer.apple.com/videos/play/wwdc2022/10135/). 오류 없는 네이티브 종료의 모든 원인을 이 코드로 확정하거나 OS 제한을 제거했다고 주장하지 않습니다.

## 실제 결과

최종 Watch 빌드 53과 Android 코드 38을 덮어 설치했습니다. 설치 후 최초 준비를 한 번 마친 사용자가 다시 워치를 암호로 잠갔고, 기기 상태에서도 `passcodeRequired=true`를 읽었습니다. 이후 워치 앱을 열지 않은 채 폰 서비스만 중지하고 22:48:24 KST에 폰의 **워치 연결**을 한 번 눌렀습니다. 폰은 새 서비스 인스턴스로 시작했습니다.

수정 후 잠금 상태에서도 요청/응답 읽기 → 양쪽 인증 → 알림 구독 완료가 기록됐습니다. 준비 전의 최종 설치본에서도 워치 `fastResumeCompleted=3`, `cancellationCount=0`, `failureCounts={}`가 읽혔고, 최종 준비 후 폰은 `authenticated=true`, `subscribed=true`, `fastResumeCompleted=12`, 오류 없음·명시적 종료 0건을 기록했습니다. 개별 인증 처리 시간은 약 2~3초였으며, 이를 검색부터 전체 연결까지의 소요 시간으로 해석하지 않습니다.

**지속 연결은 미완료입니다.** 최종 폰 기록에서는 빠른 인증 시도 24회에 완료 12회로 재시도가 남았습니다. 인증 전에 끝나는 사례와 인증·구독 뒤에 끝나는 사례가 함께 관찰됐습니다. “워치 앱을 열어야만 인증할 수 있다”는 경로는 개선했지만, 가까이 있는 동안 단절 없는 사용이나 장시간 잠금·실제 거리 복귀를 모두 해결했다고 주장하지 않습니다. 일부 Mac 개발용 터널 읽기는 시간 초과됐지만, 이어 받은 워치 자체 이벤트에도 최근 128개 중 인증·구독 완료 각각 6건, `cancel.failure` 0건과 native 종료·재시도가 함께 남았습니다. 두 앱의 완료 기록을 지속 연결 성공으로 확대하지 않습니다. Mac 개발 연결 실패와 갤럭시–워치 BLE 종료는 다른 연결입니다.

다음 남은 문제는 인증·구독 뒤 native nil-error 종료의 조건과 그 뒤 재인증의 반복입니다. 위치 활동 `eligible` 자체가 이 종료를 없애는 증거는 아니며, 같은 핸들·키를 무조건 재사용하거나 암호 검사를 생략하는 방식으로 숨기지 않습니다. 이 버전은 **수정 후보**로만 제공합니다.

작업 종료 시에는 기존 방침대로 폰의 **설정 → 연결 중지**로 실제 서비스를 중지하고 Mac 무선 디버깅을 종료합니다. 등록·키·차량 설정은 보존합니다. 평소 자동 연결을 쓰려면 폰의 **워치 연결**을 켜 두어야 합니다. 명시적인 연결 중지와 자연스러운 거리 단절은 다릅니다.

시스템 로그·관리자 암호·등록 초기화·기기 재부팅·실제 차량 명령은 사용하지 않았습니다. 기존 주 1회 Mac 서명 갱신의 설치 소스도 최종 커밋에 맞추며 지금 서명 갱신을 실행하지 않습니다. 워치 인터넷만으로 무료 자동 서명하는 목표는 별도 미완료입니다.
