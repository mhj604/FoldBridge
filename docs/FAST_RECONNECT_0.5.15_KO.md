# Android 0.6.11 / Watch 0.5.15 — 재연결 지연 줄이기

**한국어** · [English](FAST_RECONNECT_0.5.15_EN.md)

브랜치: `fix/watch-background-reconnect`. Android **0.6.11-local / 코드 29**, Watch **0.5.15 / 빌드 41**. [APK](../artifacts/android/FoldBridge-Local-0.6.11.apk).

## 실제 지연과 수정

0.5.14에서 암호 잠금 상태의 워치가 폰 조작만으로 재인증됐고 사용자도 연결 성공을 답했습니다. 해당 구간의 기기 잠금 상태는 `passcodeRequired=true`였고 인증 과정은 모두 `active=false`였습니다. 폰 서비스 재등장 이벤트부터 인증 완료까지 약 20초, 구독 완료부터 인증 완료까지 약 13초가 걸렸습니다. 폰 기록에는 연결 서비스 재시작과 새로고침 1회가 포함되므로 한 버튼의 단일 클릭 시간이라고 해석하지 않습니다.

인증 도중 일반 새로고침 `wake`가 들어오면서 워치가 진행 중인 인증을 버리고 새 nonce로 다시 시작한 기록이 있었습니다. 0.5.15는 정상 진행 중인 인증을 이어가도록 이 요청을 합칩니다. 정상 인증 단계가 15초 이상 진행되지 않은 경우에는 새로고침으로 재시작할 수 있습니다. 이 시간은 대기 타이머가 아니라 새로고침 수신 시 진행 상태를 판별하는 기준입니다.

폰도 최초 인증 요청을 이미 받았다면 남아 있는 시작 신호·깨우기 조각을 더 전송하지 않고 인증 응답으로 진행합니다. 이미 전송 중인 ATT indication의 완료 콜백은 유지해 다음 응답을 잃지 않게 합니다. 정상 인증 교환·저장된 키 확인·암호화는 유지합니다. 앱 삭제·등록 해제·차량 설정 초기화는 하지 않습니다.

## 적용 상태

2026-11-13에 양쪽 설치를 마쳤습니다. 기기 기록은 폰 0.6.11 / 코드 29와 워치 빌드 41을 보여 줍니다. 등록·키·차량 설정은 유지했습니다.

폰 업데이트로 서비스가 다시 나타난 **17:31:18 KST**부터 워치 인증 완료 **17:31:25**까지 약 **7초**, 첫 인증 쓰기 **17:31:24**부터 완료까지 약 **1초**였습니다. 해당 기록은 모두 `active=false`이고 이후에도 기기 암호 잠금 상태가 읽혔습니다. 폰의 대기 프레임·메시지·알림은 0, 오류는 없었습니다.

앞선 약 20초 사례와 이번 약 7초 사례는 같은 조건의 반복 평균이 아닙니다. 이번에는 업데이트 후 서비스 재등장·기존 BLE 링크 복원 경로이고, 설치 준비에 Mac의 화면 비활성 실행 명령도 사용했습니다. 모든 연결이 7초 또는 인증이 1초라고 보장하지 않으며 OS가 완전히 종료된 앱을 자동으로 깨운 모든 경우가 입증된 것도 아닙니다.

새 프로세스에서는 위치 기반 연결 유지 요청이 아직 실행 중이 아니어서, 업데이트 직후 기존 저장 설정을 재개할 1회 전면 초기 실행을 사용자에게 요청했습니다. 사용자가 완료를 알렸고 **17:37:28 KST** 앱 기록에서 `continuousRequested=true`, `connected=true`, `active=false`를 읽었습니다. 이는 설치 직후 준비이며 평소 연결할 때마다 앱을 열라는 요구와 구분합니다.

작업 종료 시 폰 설정의 **연결 중지**를 실행했습니다. 화면이 **워치 연결**로 돌아왔고 실제 `BridgeService`가 종료됐습니다. 등록 해제·설정 초기화는 하지 않았습니다. Mac의 폰 화면 공유와 ADB 연결도 종료했고 Device Hub는 닫힌 상태입니다.

시스템 로그·실제 차량 명령·추가 재부팅·거리 이동은 사용하지 않습니다. 예약 서명 갱신도 다시 켜지 않습니다. 앱 실행 불가의 서명 만료 복구는 [0.5.14 기록](WATCH_0.5.14_SUBSCRIPTION_AUTH_KO.md)에 남깁니다.
