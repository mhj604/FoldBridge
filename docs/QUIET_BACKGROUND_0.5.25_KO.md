# WatchBridge 0.5.25 — 백그라운드 표시와 충전 보호 알림

[English](QUIET_BACKGROUND_0.5.25_EN.md)

2026-11-17(KST). Android **0.6.19-local / 코드 41**, Watch·위젯 **0.5.25 / 빌드 59**. `fix/watch-background-reconnect`에서 진행하며, 빌드 58의 연결 복구 코드는 유지합니다. 기존 등록·키·차량 설정·설치 ID를 변경하지 않습니다.

## 배터리 보호 안내 제외

이전 필터는 `charging_state` 태그 또는 `CHR` 채널의 진행 중인 시스템 알림을 충전 상태로 인식했습니다. 사용자가 보고한 ‘배터리 보호를 위해 충전 중지됨 / 충전이 90%로 제한되었습니다’는 별도 태그·채널·재게시 키로 전달될 경우 이 조건 밖에 있을 수 있습니다. 실제 해당 기기의 새 알림 메타데이터는 아직 확보하지 않았으므로 태그 변경을 확정 원인으로 표현하지 않습니다.

새 필터는 **발신 패키지가 `com.android.systemui`인 경우에만**, 한국어·영어 제목/본문/확장 텍스트의 배터리 보호·충전 제한 의미를 인식해 워치 전송에서 제외합니다. 퍼센트·태그·알림 키가 바뀌어도 제외하며 ‘충전 상태 알림’ 옵션과 별개입니다. 새 게시와 활성 알림 재조회 양쪽에 적용하고, 기존 전송 대기에 같은 알림이 있으면 비웁니다. 원문을 기록하지 않고 제외 횟수 `suppressedBatteryProtection`만 앱 상태 파일에 남깁니다.

다른 앱 알림과 폰 자체 삼성 충전 표시는 유지합니다. 모든 SystemUI 알림을 일괄 차단하는 규칙은 아닙니다. 현재 한국어·영어 문구를 지원하며 다른 언어·새로 바뀐 표현은 추가 분류가 필요할 수 있습니다.

## 워치 화면과 백그라운드 실행

REA로 읽은 작업 시작 시 워치는 `applicationState=background`, 위치 세션 `eligible`, 인증 완료 상태였습니다. 이는 ‘화면에 계속 보이는 느낌’과 실제 백그라운드 실행이 다른 문제임을 보여주며, 사용자가 본 모든 화면 전환 원인을 확정하지는 않습니다.

소스에서 발견한 전면 실행 경로는 Mac 설치/갱신 뒤의 `devicectl device process launch`입니다. CLI 기본값이 `--activate`였으므로 이 경로를 **`--no-activate`**로 바꿨습니다. 실패하더라도 전면 실행으로 재시도하지 않습니다. 이번 기기의 비활성화 실행 요청은 성공했습니다. 차량 위젯을 사용자가 눌렀을 때 제어 창을 여는 동작은 유지합니다.

손목을 들 때 이전 앱이 다시 보이는 시간은 **watchOS 설정 → 일반 → 시계로 돌아가기 → WatchBridge → 사용자화 → 항상**에서 정합니다. 해당 앱에 ‘앱으로 돌아가기’가 있으면 끕니다. 앱에서 이 시스템 설정을 강제로 변경하는 토글을 만들지 않고, WatchBridge 설정에 정확한 안내를 추가했습니다. 위치 활동의 작은 시스템 표시까지 숨기는 변경은 아닙니다. [Apple의 시계로 돌아가기 안내](https://support.apple.com/guide/watch/adjust-the-display-settings-apd127ec93ac/27/watchos/27).

## 설치 및 남은 항목

워치 빌드 59 설치와 `--no-activate` 실행 요청이 완료됐습니다. Android 0.6.19는 기존 키로 빌드됐으며 기기 설치 상태는 아래 후속 기록을 따릅니다. 진단 번호는 양쪽 모두 실제 앱 메타데이터에서 읽도록 바꿔 이전 하드코딩 번호 오류를 없앴습니다.

- 워치 빌드 59 설치: `ev_99fd1c8c6ef74a321e3940bcfe2261d185a06fd2dc600b220c97c4e0f1fb5142`
- 전면 활성화 없는 실행 요청: `ev_52e57a021333d182395b0649c587305a48757a2655bc183583aa7dd7918e9f01`

REA CLI와 Apple `devicectl`을 감싼 프로세스 캡처를 사용했습니다. 시스템 로그·관리자 인증·등록 초기화·차량 명령은 사용하지 않았습니다. 일반 QA나 진단용 알림 발생은 진행하지 않았습니다.

수시간·밤새 잠금 및 빌드 58 이후 실제 거리 이탈/복귀는 아직 미완료입니다. 이번 표시·필터 변경을 그 조건의 해결로 확대하지 않습니다. [앞선 연결 기록](REA_0.5.24_KO.md).

설치 후 `--no-activate` 요청은 성공했지만 후속 앱 상태 파일 수집은 Mac–워치 네트워크 터널 시간 초과로 실패했습니다(`ev_d0df01e753ba4d6d865cef2fad83b7a54fff1ac87163495b2ecb68be5a7ce422`). 명령 성공과 실제 화면·새 프로세스 상태 관측을 구분합니다. Android 설치는 디버깅 포트 응답을 기다리고 있습니다.


## 최종 설치 기록 — 2026-11-17

ADB 서버를 재시작하자 같은 갤럭시 주소와 포트로 연결됐고 Android **0.6.19 / 코드 41** 덮어 설치가 완료됐습니다. 기기 등록이나 네트워크를 변경하지 않았습니다. 갤럭시 앱 자체 기록은 빌드 41·인증 완료·읽기 수신 모드를 보였습니다. 이 시점 배터리 보호 제외 횟수는 0이므로, 새 필터가 실제 해당 안내를 처리한 사례까지 관측했다고 주장하지 않습니다. 사용자가 보고한 문구를 차단하는 코드·설치가 완료된 상태입니다.

워치의 후속 파일 수집도 다시 가능해졌습니다. 실제 **빌드 59**, `active=false`, `applicationStateName=background`, 위치 `eligible`, 인증·읽기 수신 완료가 새 프로세스에서 읽혔습니다. 사용자는 워치의 시계 화면 복귀 설정을 완료했다고 알려 주었습니다.

- Android 설치: `ev_db5b722d3635ec1ab13d132f31018da009470285280a05961b7092bc73a8e6bf`
- Android 설치 후 앱 상태: `ev_cc895b1b3a6abd0d0b9421adc811825c38725e02bbd493be8c0268530ae3bb6e`
- Watch 빌드 59의 실제 백그라운드 상태: `ev_2e83e5295639bd8aa1fecf4779a413a8dd0c4643cab7aeb307ed3070d6e5858b`

자동 갱신용 비공개 소스도 설치된 빌드 59의 커밋으로 맞췄습니다. 기존 주간 예약을 바꾸거나 이번에 갱신을 실행하지 않았습니다.


## 후속 원인 조사 및 화면 설정 — 2026-11-18

같은 설치본(Android 코드 41, Watch 빌드 59)의 REA 앱 자체 기록을 읽었습니다. 양쪽 모두 인증 및 읽기 수신이 완료돼 있었습니다. 워치 기록에는 이전에 GATT 서비스 검색이 대기하다가 `active=false` 상태에서 인증·읽기 수신으로 진행한 이력이 있습니다. 최초 불연결을 보고한 시점과 수집 시점 사이에 시간 차이가 있어, 이 기록만으로 당시 폰 서비스 중지와 서비스 검색 지연 중 어느 쪽이 원인이었는지는 확정하지 않습니다. 앱이 열려야만 인증된다고도 단정할 수 없습니다.

화면 문제는 별도로 조사했습니다. 워치의 동일 프로세스가 `active=false`, `applicationStateName=inactive`로 남아 있었습니다. `inactive`는 실제 `background`와 다르며, 이전 `lifecycle.background` 이벤트는 SwiftUI가 active가 아닐 때 찍혀 두 상태를 구분하지 못합니다. 이 이벤트 이름만 보고 앱이 백그라운드였다고 판단하지 않습니다. 폰의 `watchActive` 역시 연결 유지 실행 가능 여부를 포함해, 화면 표시 여부와 동일하지 않습니다.

REA가 지원하지 않는 워치 화면 조작은 Mac Device Hub를 통해 별도로 진행했습니다. 직접 읽은 시스템 설정은 다음과 같습니다.

- WatchBridge의 **시계로 돌아가기 → 사용자화 → 항상**은 이미 선택돼 있었습니다. 이 기기의 해당 페이지에는 **앱으로 돌아가기** 토글이 없었습니다. 앞선 안내의 조건부 토글을 모든 기기에 존재하는 것으로 설명하지 않습니다.
- **스마트 스택 → 실시간 현황 허용**은 이미 꺼져 있었습니다.
- **손쉬운 사용 → 앱 전환기 → 초점이 맞춰진 앱 자동 선택**은 켜져 있었습니다. 시스템 안내대로 앱 전환기에서 초점이 1초 유지되면 탭 없이 해당 앱을 여는 경로입니다. 이를 **끔**으로 변경하고 시계 화면으로 돌아갔습니다. 이 시스템 설정은 WatchBridge뿐 아니라 모든 앱의 전환기에 적용됩니다. BLE 등록·연결 유지·키·차량 설정은 변경하지 않았고 새 앱 빌드는 설치하지 않았습니다.

이는 탭 없이 앱을 여는 확인된 시스템 경로를 제거한 조치입니다. 사용자가 겪은 모든 화면 복귀의 단일 원인으로 확정하거나 이후 재발이 없다고 주장하지 않습니다. 위치 세션의 표시와 앱 전환기의 자동 선택은 별개입니다. [Apple의 초점 앱 자동 선택 안내](https://support.apple.com/ko-kr/guide/watch/apd081746d24/27/watchos/27).

추가로 폰의 `suppressedBatteryProtection=20`이 관측됐습니다. 배터리 보호 필터가 실제 게시를 제외한 사례가 이제 기록됐습니다. 시스템 알림 원문이나 개인 알림 내용은 공개하지 않습니다.

REA Evidence:

- 워치 상태: `ev_c54d763f7ce352d8e58987d6ea6f1d5f6baf1ae5386b632ac5b1a4d1280a166f`
- 워치 앱 자체 이벤트: `ev_56bf488a356909c1275e41abb99bcdfa635f3e5c54aaf9f1d5946918fe72b676`
- 폰 상태: `ev_d707645aafc484a2ed4c78d60bae9daf83132da5df2ead63169fbcde3f649bc8`

이번 작업은 앱 기록 기반 원인 조사와 실제 설정 변경이며 일반 QA, 인위적 알림·거리 이탈·강제 끊김 실험은 수행하지 않았습니다. 장시간 잠금 및 빌드 58 이후 실제 거리 복귀의 남은 범위는 그대로입니다.


### 사용자 추가 설명: 손목을 들거나 화면을 켤 때 표시됨

사용자는 앱 전환기를 보고 있을 때가 아니라 **손목을 들거나 화면을 켤 때** WatchBridge가 보인다고 명확히 했습니다. 따라서 앞서 끈 자동 선택 기능을 이 증상의 확정 원인·완료된 해결로 취급하지 않습니다.

[Apple의 백그라운드 세션 문서](https://developer.apple.com/documentation/watchkit/enabling-background-sessions)는 위치·오디오·운동 세션 중 손목을 들면 앱이 표시되는 동작을 설명합니다. 현재 `LocationKeepAlive`는 `CLBackgroundActivitySession`과 위치 업데이트를 유지하므로 보고된 현상과 맞는 경로입니다. 이는 문서·코드와 사용자 설명에 근거한 원인 후보이며 별도 기기 실험은 수행하지 않았습니다. 앱 전환기 자동 선택과 다른 문제입니다.

**미해결:** 위치 기반 실행 시간을 유지하면서 세션의 손목 들기 화면 복귀를 앱 코드만으로 억제하는 적용 가능한 방법은 아직 확보하지 못했습니다. 현재 기기에는 해당 세션용 ‘앱으로 돌아가기’ 토글이 없습니다. Always On 표시만 끄는 방법도 화면을 켤 때의 복귀를 해결하지 않습니다. 화면을 감추려고 연결 유지 세션을 종료하거나 프로세스를 종료하는 변경은 적용하지 않았습니다. 기존 앱 버전·등록을 유지합니다.

종료: 사용자가 폰의 **연결 중지**를 눌렀다고 확인했습니다. Mac Device Hub 화면 공유와 ADB 연결은 이미 종료됐습니다. 사용자 확인 이후 앱 파일을 다시 읽지는 않았습니다.
