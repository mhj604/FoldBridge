# WatchBridge 0.5.24 — 잠금 중 읽기 수신

[English](REA_0.5.24_EN.md) · [앞선 REA 조사](REA_0.5.23_KO.md)

2026-11-15. Android **0.6.18-local / 코드 40**, Watch·위젯 **0.5.24 / 빌드 57** 수정 후보입니다. 기존 등록·키·차량 설정을 유지하고 덮어 설치했습니다. [APK 다운로드](https://github.com/mhj604/WatchBridge/releases/download/watchbridge-v0.5.24/WatchBridge-0.6.18.apk).

## 추가로 좁힌 문제

빌드 55에서는 워치가 암호로 잠긴 것을 Apple 기기 상태에서 읽고 폰의 **워치 연결**만 눌렀습니다. 워치 앱을 열지 않은 채 인증·알림 구독이 완료됐고, 인증 처리 자체는 폰 약 104ms·워치 약 161ms였습니다. 이는 검색부터 전체 연결까지의 시간이 아닙니다.

유휴 연결은 2분 이상 유지됐지만, 진단 알림 1건을 보내자 워치의 수신·표시 횟수가 늘기 전에 오류 없는 종료와 재인증이 발생했습니다. 폰은 전달 요청을 기록했지만 수신 확인은 없었습니다. 따라서 인증 속도·화면 문구만의 문제가 아니라 **indication 수신 경로에서 다시 단절이 발생하는 조건**을 분리했습니다. 이 한 사례로 watchOS 내부의 특정 버그나 예산 소진을 확정하지 않습니다.

## 바꾼 방식

저장된 상대와 빠른 인증을 마친 뒤, 양쪽이 지원하고 워치의 위치 연결 유지가 켜져 있으면 **읽기 수신 모드**를 암호화된 메시지로 합의합니다. 워치가 새 읽기 특성에서 기존 암호화 프레임을 가져오므로, 해당 모드에서는 알림 본문 수신을 위해 TX indication 구독을 켜지 않습니다.

데이터가 있으면 다음 프레임을 이어 읽고, 비어 있으면 앱이 실행 중인 동안 약 2초 뒤 다시 읽습니다. 원본 아이콘·알림 내용의 기존 분할·조립·암호 검증·수신 확인을 사용합니다. 차량 버튼 목록과 결과도 같은 경로로 전달됩니다. 기존 UUID·키는 바꾸지 않고 읽기 특성을 추가했습니다. 신규 최초 등록과 이전 버전 상대는 기존 indication 방식을 유지합니다. [전송 규칙](PROTOCOL.md#0524--android-0618-읽기-기반-수신).

폰의 연결 표시는 읽기 모드에서 최근 10초 이내 실제 읽기 요청도 요구합니다. 앱 실행이 멈춰 읽기가 오래 중단되면 응답 대기로 표시하고, 재개 시 이전 미전달 대기열은 비워 수치·메시지가 한꺼번에 몰려오지 않도록 합니다. 새 인증 때도 이전 대기열을 비웁니다. 폰 새로고침은 이 모드를 지원하며 등록을 지우지 않습니다.

## 실제 관측

읽기 경로의 빌드 56 설치 후 최초 준비를 한 번 마치고 다시 암호로 잠갔습니다. Apple 기기 상태의 `passcodeRequired=true`, 워치 앱 상태의 `applicationState=2 / background`, 위치 `eligible`을 읽었습니다. 이는 이전 `inactive` 기록과 구분합니다.

읽기 수신 모드가 양쪽에서 켜졌고, 진단 알림 1건을 **29개 프레임**으로 받아 워치 표시 요청까지 완료했습니다. 워치 수신·표시 카운터는 **2448 → 2449**, 폰 수신 확인은 **0 → 1**, 대기는 **0**이었습니다. 해당 구간에서 재인증은 1회 완료 상태를 유지했고, 종료·앱 취소·프레임 폐기·검증 실패는 관측되지 않았습니다. 같은 근거리 유휴 연결 결과만으로 모든 장시간·거리 복귀 조건이 해결됐다고 확대하지 않습니다.

## 조건과 미완료 범위

읽기 타이머는 watchOS 실행 기회를 만들지 못합니다. 위치 연결 유지가 실제로 실행 기회를 제공하는 동안 동작하며 배터리 사용이 늘 수 있습니다. 앱이 중단·종료되거나 시스템이 실행을 허용하지 않는 상황까지 모든 알림을 무조건 깨워 받는다고 주장하지 않습니다. [Apple의 백그라운드 실행 설명](https://developer.apple.com/documentation/watchkit/using-background-tasks).

실제 거리 복귀와 장시간 잠금의 관측 결과는 추가 기록하며, 수시간·밤새 잠금이나 시스템에 의한 프로세스 종료까지 완료로 표시하지 않습니다. 폰 서비스를 사용자가 **연결 중지**한 상태는 자동 재연결 대상이 아닙니다. 작업을 마칠 때는 요청된 방침대로 등록은 보존하고 실제 연결만 중지합니다.

## 실제 거리 이탈에서 찾은 추가 문제와 빌드 57

사용자가 워치를 암호 잠금 상태로 멀리 가져갔습니다. 폰 기록은 먼저 ‘워치 응답 대기’, 이어 `centralPresent=false`, `authenticated=false`, 광고 재개를 보였습니다. 돌아온 뒤에도 워치가 `background / eligible`, 네이티브 `connecting`에 머물렀고 새 인증은 시작하지 않았습니다. 따라서 단순 유휴 기록으로 거리 복귀가 해결됐다고 보지 않습니다.

빌드 54의 검색 억제가 실제 거리 시간 초과 후의 복구 검색까지 막은 경로를 보완했습니다. 빌드 57은 실제 연결 시간 초과·상대 단절 또는 복원된 기존 연결 대기에서 한 복구 구간에 하나의 서비스 필터 검색을 허용합니다. 기존 네이티브 연결 요청은 유지합니다. nil-error 알림 단절마다 검색을 다시 켜던 동작은 되돌리지 않습니다. 새 광고에서 다른 주변 기기 객체를 얻더라도 저장된 상대 키로 다시 인증하며 등록을 지우지 않습니다.

폰의 재광고 주소가 실제로 바뀌었는지까지 이전 기록으로 확정하지는 않습니다. 관측된 원인은 ‘광고 중인 폰을 두고 기존 네이티브 대기만 유지하며 복구 검색 경로를 막은 것’의 범위입니다. 빌드 57의 설치·관측 결과는 아래에 추가합니다.
