## 직접 수행한 조건과 결과

사용자가 워치를 암호로 잠근 뒤, REA CLI로 갤럭시 Bluetooth를 끄고 다시 켰습니다. 저장된 등록은 유지했고 워치 앱 실행·새로고침·폰 연결 버튼을 사용하지 않았습니다. 각 회차에서 실제 인증 링크 종료를 먼저 확인했습니다.

| Bluetooth 중단 | 자동 인증·수신 복원 | 켜기 요청부터 최초 정상 수신 표본까지 | 폰 native 종료 누적 |
| --- | --- | --- | --- |
| 30초 | 성공 | 약 11초 | 0 → 1 |
| 60초 | 성공 | 약 5초 | 1 → 2 |
| 90초 | 성공 | 약 10초 | 2 → 3 |

표의 시간은 약 5초 간격 상태 읽기와 도구 실행 시간을 포함합니다. 실제 연결이 완료된 순간을 정밀 측정한 값이나 항상 보장되는 지연 시간이 아닙니다.

- 워치 자체 상태에서 실제 백그라운드 실행과 복원 후 인증을 확인했습니다. 60초·90초 중단 중에도 광고 없는 시간 경과만으로 연결을 취소한 횟수는 0이었습니다.
- 마지막 복원 뒤 명시적인 테스트 알림 1건을 보냈습니다. 폰 전달·수신 확인이 각각 1 증가했고 대기열은 0이 됐습니다. 워치 수신·표시 요청도 각각 2771 → 2772로 증가했습니다. 이는 앱 전달과 OS 표시 요청 기록이며 잠긴 화면에서 사람이 팝업을 보았다는 뜻은 아닙니다.
- Bluetooth는 각 회차 종료 때 다시 켰습니다. 등록·차량 설정은 삭제하지 않았습니다.

## 잠금 상태 연속 관찰

10분(600.89초) 동안 30초 간격으로 읽은 **21개 표본 모두 인증 링크·수신 준비가 정상**이었습니다. 폰 native 종료 누적은 3 → 3으로 추가 종료가 없었고, 읽기 요청은 1732 → 2147로 증가했습니다. 10초 이상 읽기 재개 간격 카운터는 0, 마지막 대기열은 0이었습니다.

관찰 중간에 워치의 `passcodeRequired=true`도 다시 읽었습니다. 마지막 워치 이벤트 파일 복사는 Mac–워치 개발 터널 시간 초과로 실패했습니다. 따라서 끝 시점의 워치 이벤트 전부를 대조했다고 표현하지 않으며, 폰의 지속 인증·읽기 기록과 앞서 수집한 워치 백그라운드 기록을 근거로 합니다. 개발 터널 실패 중에도 폰 BLE 수신 상태는 유지됐습니다.

## 남은 범위

3회 모두 앱을 열지 않고 자동 복원됐습니다. 다만 Bluetooth를 끈 시험은 실제 거리를 이동한 시험과 다릅니다. **수시간/밤새 잠금, 반복적인 실제 거리 이탈·복귀, OS 프로세스 종료 뒤 복원**은 이 결과만으로 완료 처리하지 않습니다.

이번 회차의 `proximityRearms`와 연결 취소 횟수는 0이었습니다. 정상 native 재연결이 작동했으므로 0.5.28의 취소 완료·광고 기반 재설정 분기가 모두 실행됐다고 주장하지 않습니다. 메인 화면 자동 표시 문제는 계속 보류합니다.
